每个工作包只有一个当前实现者和一个验收者。主控加最多三个执行/审查 Agent 构成一轮；不得因任务表有多个角色就默认这些角色已经运行。WorkBuddy 与 Agent 即使能访问同一目录，也不同时编辑相同文件。

优先在独立 checkout 中开发，并以基线提交、patch/提交及测试记录交接；若当前只能共享工作区，则使用本表的文件所有权，禁止其他 Agent 切换全局分支或覆盖未提交文件。没有提交基线之前只开展环境/来源检查及隔离文档工作。

## 6. WorkBuddy交接与回收协议

主控通过实际验证的入口派发任务，不猜测WorkBuddy API或CLI。WB-01任务单只允许写 `collaboration/workbuddy/results/`；用户已要求WorkBuddy协助开发，但“发出任务”“收到结果”“验收结果”仍是三个不同状态。主控根据实际观察单独更新派发状态；本工作包初始任务板统一为planned。

每次任务单包含：任务ID、基线提交或清单、契约版本、允许读写目录、禁止修改项、输入样本、期望操作、失败处理、验收方法、输出路径与结果结构。涉及产品代码时，另分配独立checkout/分支和文件所有权；首包没有这项权限。

结果至少列出：task_id、执行开始/结束时间、执行者/工具、实际命令或请求、观察、产物路径、校验结果、未验证项、阻塞、下一步建议。凭证及完整环境变量不得写入结果。联网失败保留失败事实，不改为“来源不存在”；仅检查首页也不能宣称增量、正文、历史和许可全已通过。

回收步骤：主控读取产物→复核范围及真实性→必要时复跑关键命令→独立验收→将已确认结论写入文档；来源正式配置需额外通过接入门槛→任务板标done。返回的报告和代码同样是参考输入，不能自动获得修改共享契约或扩大任务范围的权力。

## 7. 状态、变更与每轮交付

任务状态采用planned、dispatched、in_progress、review、done、blocked。planned表示尚未执行；dispatched仅代表实际派发；review表示实现者交付但未通过验收；blocked需写明阻塞原因及解除条件。状态不能仅依据角色分配或文件存在自动升级。

每轮交付记录基线、修改文件、测试命令及结果、产物、风险、未验证项、下游影响。需要公共契约变更时先提交变更提案，主控检查调用方、数据迁移及回归影响后统一整合。不得覆盖已有文档、未提交代码或他人正在写的文件。

开始产品模块并行实现前的最小可观察成功条件：G0通过、G1样例可用、至少一项真实来源探测有证据、每个并行工作包有唯一文件所有者和验收者。环境与契约尚在建立时，可由主控先做隔离的纯标准库离线验证原型，并提供 `scripts/dev.ps1` 自动定位可用解释器；fixture→证据/事件→截点简报与manifest用于检验方案，不等于正式采集、LLM或全G0/G2已验收。不存在完整前置条件时先完成基础工作，不以多Agent数量代替可交付进度。
